Week 3 follow-up -- Gatekeeper boundary stress test
============================================================

Motivation: gatekeeper_metrics.txt's honest caveat noted that 0 of 26
non-divergent real validation chips sit within 2 Hz of the -0.5 Hz
SUCCESS/FAILURE threshold, so the Task 1 gatekeeper's 100% accuracy never
actually tested the hard, near-boundary case. This script builds
60 synthetic chips with TRUE final delta_f drawn uniformly from
[-3.5, 2.5] Hz (threshold +/- 3.0 Hz) and runs
the SAME trained gatekeeper (pipeline_api.train_gatekeeper(), identical
features/training data to gatekeeper_model.py) against them.

Overall accuracy on this near-boundary batch: 0.917

Accuracy by distance from threshold (non-divergent chips only --
divergent chips are a separate failure mode, not a boundary-proximity one):
  |true_delta_f - threshold| in [0,0.5) Hz: n=5, accuracy=0.600
  |true_delta_f - threshold| in [0.5,1.0) Hz: n=2, accuracy=0.500
  |true_delta_f - threshold| in [1.0,2.0) Hz: n=2, accuracy=1.000
  |true_delta_f - threshold| in [2.0,3.0) Hz: n=5, accuracy=0.600

INTERPRETATION: accuracy drops meaningfully near the boundary -- this is the honest answer
the earlier caveat predicted might exist. The gatekeeper's real-world 100%
should be read as 'validated on the chips this dataset actually has', not
'reliable arbitrarily close to -0.5 Hz' -- worth flagging to Eva/the teacher
as a genuine performance boundary, not a bug to silently patch away.

UPDATE (multi-window curve-shape features): the gatekeeper was retrained
with early_displacement_15s and early_displacement_45s added alongside the
original 30s value and divergence flag (gatekeeper_model.EXTRA_WINDOWS) --
giving it the early trend across three points instead of one, on real data
for validation chips (biomarker_window_reconciliation.py's baseline logic)
and the already-generated resampled curves for synthetic training chips (no
new RNG draw). Result, same 60-chip stress batch:
  Overall accuracy: 0.917 -> 0.917 (unchanged)
  SUCCESS recall:   0.44  -> 0.67  (real improvement -- this was the
                                     specific weak point flagged before)
  FAILURE recall:   not separately reported before -> 0.80 now
Per-band accuracy at this n (5/2/2/5 per band) is noisy and should not be
over-read -- the [0,0.5) Hz band actually went 0.80 -> 0.60, while
[0.5,1.0) Hz went 0.0 -> 0.50. The honest takeaway is the aggregate SUCCESS
recall genuinely improved with no cost to overall accuracy, not that the
boundary problem is solved -- accuracy this close to the threshold is still
well below the 100% seen on real validation chips, none of which sit this
close to begin with.
